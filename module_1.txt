# Specification: Digital Aggregators Partner Portal

## Purpose

This specification defines the behavioral contract for the Digital Aggregators Partner Portal, a secure, multi-tenant platform for managing leads, documents, analytics, finance, ticketing, knowledge, and notifications for digital aggregator partners. The system SHALL enforce strong RBAC, geo-scoping, and audit logging, and SHALL integrate with external authentication, payment, AV scanning, notification, CDN, and analytics/monitoring systems.

---

## Technologies and Runtime Stack

- **Languages:** Node.js, Java, Python, Go, Scala
- **Frameworks:** Express, Spring Boot, FastAPI
- **Frontend:** ReactJS, React Native, PWA
- **API Gateway:** Kong, Apigee, Nginx
- **Databases:** PostgreSQL (Row Level Security), MongoDB, Cassandra, Elasticsearch
- **Cache:** Redis (Clustered)
- **Object Storage:** S3, Azure Blob Storage
- **Messaging:** Kafka, RabbitMQ, SQS
- **Auth:** OAuth2, JWT, SAML, Keycloak, Auth0, OPA, Casbin
- **Notifications:** Twilio, SendGrid, AWS SNS
- **AV Scanning:** ClamAV, VirusTotal
- **CDN:** CloudFront, Azure CDN, Fastly
- **Monitoring:** Prometheus, Grafana, ELK Stack
- **Infra:** Kubernetes (EKS/AKS/GKE), Istio, Terraform

## Components

### API Gateway (SVC-API-GW)
- **Responsibilities:** Unified ingress, authentication (OAuth2/JWT), RBAC policy enforcement, protocol mediation, centralized logging, versioning, and throttling.
- **Technologies:** Kong, Apigee, Nginx, OpenAPI/Swagger

### Lead Management Microservice (SVC-LEAD-MGMT)
- **Responsibilities:** Lead intake, deduplication, enrichment, status tracking/eventing, lifecycle, and data partitioning.
- **Technologies:** Node.js/Express or Java/Spring Boot, Kafka/RabbitMQ, PostgreSQL/NoSQL

### Document Management Microservice (SVC-DOC-MGMT)
- **Responsibilities:** Document uploads/downloads, virus scanning, PII masking, secure storage, and policy-driven access.
- **Technologies:** Python/Go, S3/Blob Storage, ClamAV, Pre-signed URL system

### Analytics & Reporting Microservice (SVC-ANALYTICS)
- **Responsibilities:** Business metric aggregation, reporting, geo-analytics, funnel/conversion/statistics, CQRS read models.
- **Technologies:** Python/FastAPI or Scala/Spark, OLAP DB/ClickHouse/BigQuery, Elasticsearch

### Finance & Payouts Microservice (SVC-FINANCE)
- **Responsibilities:** Partner payouts, invoices, commissions, disputes, and taxes.
- **Technologies:** Java/Spring Boot, SQL DB, PDF Generator

### User & Access Management Microservice (SVC-USER-MGMT)
- **Responsibilities:** Onboarding, RBAC policy, geo-scoping, access audits, session management.
- **Technologies:** Java/Spring Boot, Keycloak/Auth0, SQL/LDAP

### Ticketing & Communication Microservice (SVC-TICKETING)
- **Responsibilities:** Support tickets, communication, announcements.
- **Technologies:** Node.js/Express, SQL/NoSQL DB, WebSocket

### Knowledge Hub / Compliance Microservice (SVC-KNOWLEDGE)
- **Responsibilities:** Training/media resources, certifications, static/rich content streaming.
- **Technologies:** Node.js/Python, CMS/Media Streaming

### RBAC Infrastructure Service (SVC-RBAC)
- **Responsibilities:** Central RBAC policy enforcement, permissions API/service, geo-based scoping.
- **Technologies:** OPA (Open Policy Agent), Keycloak, Casbin

### Audit Logging Service (SVC-AUDIT)
- **Responsibilities:** Immutable audit trails for all sensitive actions.
- **Technologies:** Append-only Log Store, Kafka Streams, Elasticsearch

### Notification Service (SVC-NOTIFY)
- **Responsibilities:** Multi-channel notifications (in-app, email, SMS, webhooks), delivery tracking.
- **Technologies:** Node.js/Python, Twilio/SendGrid/SNS, Webhook Engine

### Messaging/Event Streaming Service (SVC-MSG-BUS)
- **Responsibilities:** Message/event brokering, async business/event workflows, decoupled bulk processing.
- **Technologies:** Kafka, RabbitMQ, SQS

## APIs

### Lead Management

#### POST /leads
- **Purpose:** Create a new lead.
- **Inputs:** Lead data (partner_id, customer info, source, etc.)
- **Outputs:** Created lead object with lead_id.
- **Main Flow:** Validate input → Deduplicate → Enrich → Persist → Publish event → Return lead.

#### GET /leads
- **Purpose:** List leads with filters.
- **Inputs:** Query params (partner_id, status, date range, pagination)
- **Outputs:** List of leads.
- **Main Flow:** Validate RBAC → Query DB → Return filtered leads.

#### GET /leads/{leadId}
- **Purpose:** Get lead details.
- **Inputs:** leadId (path param)
- **Outputs:** Lead object.
- **Main Flow:** Validate RBAC → Query DB → Return lead.

#### PUT /leads/{leadId}
- **Purpose:** Update lead.
- **Inputs:** leadId (path param), updated fields
- **Outputs:** Updated lead object.
- **Main Flow:** Validate RBAC → Update DB → Publish event → Return lead.

#### POST /leads/bulk
- **Purpose:** Bulk lead intake.
- **Inputs:** Array of lead data
- **Outputs:** Bulk result (success/failure per lead).
- **Main Flow:** Validate input → Deduplicate → Enrich → Persist → Publish events → Return results.

#### GET /leads/{leadId}/documents
- **Purpose:** List documents associated with a lead.
- **Inputs:** leadId (path param)
- **Outputs:** List of document metadata.
- **Main Flow:** Validate RBAC → Query DB → Return documents.

## Interactions with Dependencies

### External Authentication Providers (OAuth2/SAML)
- **Protocol:** OAuth2, OpenID Connect, SAML
- **Calls:** User authentication, SSO, token validation
- **Payloads:** JWT tokens, user claims
- **Error/Retry:** Retry on transient errors; fail-closed on auth failure

### Payment/Tax Processing Platforms
- **Protocol:** HTTPS REST API
- **Calls:** Initiate payout, validate transaction, generate tax docs
- **Payloads:** Payout request, transaction status, tax document
- **Error/Retry:** Retry on transient errors; log and alert on persistent failure

### Malware Scanning Service (ClamAV, VirusTotal)
- **Protocol:** API, queue
- **Calls:** Submit document for scan, retrieve scan result
- **Payloads:** File reference, scan status
- **Error/Retry:** Retry on transient errors; quarantine on persistent failure

### Email/SMS Gateway (Twilio, SendGrid, AWS SNS)
- **Protocol:** SMTP, HTTPS API
- **Calls:** Send email, send SMS, send push notification
- **Payloads:** Notification message, delivery status
- **Error/Retry:** Retry on transient errors; log and alert on persistent failure

### CDN (CloudFront, Azure CDN, Fastly)
- **Protocol:** HTTPS
- **Calls:** Serve static assets, media, training content
- **Payloads:** Asset URL, cache headers
- **Error/Retry:** Fallback to origin on cache miss

### Analytics/Monitoring Platform (ELK, Prometheus, Grafana)
- **Protocol:** HTTPS/API
- **Calls:** Export logs, metrics, analytics data
- **Payloads:** Log entries, metric data
- **Error/Retry:** Buffer and retry on transient errors

### Partner IT Systems (API/Webhook/Bulk)
- **Protocol:** HTTPS REST, Webhook, Bulk CSV/Excel
- **Calls:** Push/pull leads, docs, notifications
- **Payloads:** Lead data, document metadata, notification events
- **Error/Retry:** Retry on transient errors; log and alert on persistent failure

## Key Flows

### Lead Intake Flow
1. User submits lead via UI or API.
2. API Gateway authenticates and authorizes request.
3. LeadController receives request.
4. LeadService validates, deduplicates, and enriches lead.
5. LeadRepository persists lead to PostgreSQL.
6. LeadEventPublisher publishes lead event to Kafka.
7. NotificationService sends notification to partner.
8. AuditService logs the action.
9. Response returned to user.

### Document Upload Flow
1. User uploads document via UI or API.
2. API Gateway authenticates and authorizes request.
3. DocumentController receives request.
4. DocumentService validates and stores file in S3.
5. AVScanClient triggers AV scan.
6. DocumentRepository persists metadata to PostgreSQL.
7. AuditService logs the action.
8. Response returned to user.

### Payout Flow
1. Finance user requests payout via UI or API.
2. API Gateway authenticates and authorizes request.
3. FinanceController receives request.
4. FinanceService calculates and validates payout.
5. PaymentGatewayClient initiates payout with external platform.
6. FinanceRepository persists payout record.
7. NotificationService notifies partner.
8. AuditService logs the action.
9. Response returned to user.

### User Onboarding Flow
1. Admin creates user via UI or API.
2. API Gateway authenticates and authorizes request.
3. UserController receives request.
4. UserService validates and assigns roles.
5. UserRepository persists user to PostgreSQL.
6. SSOClient provisions user in external SSO.
7. AuditService logs the action.
8. Response returned to admin.

### Ticket Creation Flow
1. User creates ticket via UI or API.
2. API Gateway authenticates and authorizes request.
3. TicketController receives request.
4. TicketService creates and assigns ticket.
5. TicketRepository persists ticket to PostgreSQL.
6. NotificationService notifies support team.
7. AuditService logs the action.
8. Response returned to user.

## Requirements and Scenarios

### Requirement: Lead Intake SHALL Support Deduplication

#### Scenario: Duplicate Lead Submitted
- **Given** a lead with the same customer_email and partner_id already exists
- **When** a new lead with the same customer_email and partner_id is submitted
- **Then** the system SHALL reject the duplicate and return an error

### Requirement: Document Upload SHALL Trigger AV Scan

#### Scenario: Document Uploaded
- **Given** a user uploads a document
- **When** the document is stored in S3
- **Then** the system SHALL trigger an AV scan and update scan_status

### Requirement: RBAC SHALL Be Enforced on All APIs

#### Scenario: Unauthorized Access Attempt
- **Given** a user without the required role
- **When** the user attempts to access a restricted API
- **Then** the system SHALL return a 403 Forbidden error

### Requirement: Audit Logging SHALL Be Immutable

#### Scenario: Sensitive Action Performed
- **Given** a user performs a sensitive action (e.g., delete document)
- **When** the action is completed
- **Then** the system SHALL write an immutable audit log entry

### Requirement: Notifications SHALL Support Multiple Channels

#### Scenario: Notification Sent
- **Given** a platform event triggers a notification
- **When** the notification is processed
- **Then** the system SHALL send the notification via the configured channel (in-app, email, SMS, webhook)
